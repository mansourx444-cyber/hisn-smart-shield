# ٢. طريقة العمل على GitHub والتعامل مع الكود

المستودع: <https://github.com/mansourx444-cyber/hisn-smart-shield>

## ٢.١ القواعد الذهبية
1. **`main` دائمًا يعمل.** هو اللي ينشر تلقائيًا على Render ويشوفه المحكّمون. لا نكتب عليه مباشرة.
2. **كل مهمة = فرع + Pull Request.**
3. **لا أسرار في الكود.** المفاتيح (`OPENAI_API_KEY`…) في متغيرات البيئة أو `.env` (موجود في `.gitignore`).
4. **الاختبارات تنجح قبل الدمج:** `npm test`.

## ٢.٢ الفروع
| الفرع | الاستخدام | مثال |
|---|---|---|
| `main` | النسخة المستقرة المنشورة | — |
| `feat/...` | ميزة جديدة | `feat/whatsapp-group-scam` |
| `fix/...` | إصلاح خلل | `fix/header-overlap` |
| `docs/...` | توثيق فقط | `docs/meeting-notes` |
| `demo/...` | تعديل على العرض أو النصوص | `demo/final-script` |

## ٢.٣ دورة العمل اليومية
```bash
git checkout main && git pull                 # ١. ابدأ من آخر نسخة
git checkout -b feat/اسم-قصير                  # ٢. فرع جديد للمهمة
# ... عدّل واختبر محليًا: node server.js ثم npm test
git add -A && git commit -m "feat: وصف قصير"   # ٣. حفظ
git push -u origin feat/اسم-قصير               # ٤. رفع
# ٥. افتح Pull Request على GitHub واطلب مراجعة من زميل
```

## ٢.٤ رسائل الحفظ (Commits)
صيغة: `النوع: وصف بصيغة الأمر` — قصيرة وواضحة.

| النوع | متى |
|---|---|
| `feat` | ميزة جديدة |
| `fix` | إصلاح خلل |
| `docs` | توثيق |
| `test` | اختبارات |
| `refactor` | إعادة تنظيم بدون تغيير السلوك |
| `style` | تنسيق وواجهة |

أمثلة: `feat: كشف روابط النطاق الفرعي المنتحل` — `fix: تداخل الترويسة في الشاشات الصغيرة`

## ٢.٥ Pull Request
- العنوان بنفس صيغة الـ commit.
- الوصف يجاوب: **ماذا تغيّر؟ لماذا؟ كيف اختبرته؟** (القالب يظهر تلقائيًا من `.github/pull_request_template.md`).
- مراجع واحد على الأقل يوافق قبل الدمج.
- الدمج بأسلوب **Squash and merge** عشان يبقى تاريخ `main` نظيف.
- بعد الدمج: احذف الفرع.

## ٢.٦ المهام (Issues)
- كل خلل أو فكرة = Issue بالقالب المناسب (خلل / ميزة).
- التصنيفات (Labels): `bug` `feature` `demo` `docs` `priority:high`.
- ربط الـ PR بالمهمة: اكتب في الوصف `Closes #12` فتُغلق تلقائيًا عند الدمج.
- لوحة **Projects** بثلاثة أعمدة: To do ← In progress ← Done.

## ٢.٧ مراجعة الكود — ماذا نراجع؟
- هل يعمل؟ (جرّبه محليًا)
- هل الاختبارات ناجحة؟ هل يحتاج اختبار جديد؟
- هل النص العربي واضح وبدون تشكيل في الواجهة؟
- هل يحفظ أي بيانات شخصية؟ (يجب ألا يحفظ)
- هل يعمل بالعربي والإنجليزي؟

## ٢.٨ الإصدارات
قبل كل عرض نضع وسمًا (tag) للنسخة المعروضة حتى نرجع لها إذا احتجنا:
```bash
git tag -a v1.0-final -m "نسخة العرض النهائي" && git push origin v1.0-final
```
